# MultiAgentCom 技术选型决策文档（Tech Stack Decision v0.1）

> 本文用于统一技术决策，解释“选什么、为什么、不选什么、未来怎么演进”。  
> 对齐文档：`docs/Architecture-Blueprint.md`、`docs/MVP-Plan.md`、`docs/Implementation-Backlog.md`。

## 1. 决策目标

- 在 MVP 阶段优先保证“可实现、可维护、可扩展”。
- 控制复杂度，避免过早引入重型基础设施。
- 为后续生产级演进预留清晰迁移路径。

## 2. 决策原则

- **简单优先：** 同等条件下优先选择团队更熟悉、落地更快的方案。
- **可替换性：** 关键组件要有抽象层，避免强耦合。
- **一致性：** 技术栈尽量减少风格分裂与维护成本。
- **可观测：** 任何核心链路都必须具备可追踪能力。
- **演进友好：** MVP 可运行，后续可平滑升级而不推翻重来。

## 3. 技术选型总览

- 后端语言：**Go**
- 后端框架：**Gin（主选）**
- 前端框架：**Vue 3 + Vite**
- 元数据数据库：**PostgreSQL**
- 缓存/消息：**Redis（缓存 + Stream）**
- 对象存储：**MinIO（本地）/ S3 兼容（线上）**
- 沙盒隔离：**Docker 容器**
- 部署编排：**docker-compose（MVP）**
- 可观测基线：**结构化日志 + 指标采集 + 基础告警**

## 4. 分层选型决策

## 4.1 后端语言：Go

### 主选理由
- 并发模型适合调度器、任务执行器、网关服务。
- 部署简单，单二进制，容器化友好。
- 性能稳定，内存与 CPU 资源成本可控。

### 备选与放弃理由
- **Node.js：** 生态丰富，但在高并发调度与类型约束上相对弱。
- **Python：** 适合 AI 侧实验，但核心编排层性能和并发模型不占优。

### 结论
- 核心平台服务使用 Go；AI 工具型 Worker 可保留 Python 扩展能力。

## 4.2 后端 Web 框架：Gin

### 主选理由
- 学习与落地成本低，社区成熟。
- 性能足够支撑 MVP 阶段。
- 中间件体系完善（鉴权、日志、恢复、限流）。

### 备选与放弃理由
- **Fiber：** 速度快，但团队若对其生态不熟，调试成本可能更高。
- **Echo：** 也可行，但与 Gin 相比团队普及度略低（按常见团队经验）。

### 结论
- MVP 采用 Gin；若后续有明确性能瓶颈再评估迁移。

## 4.3 前端技术：Vue 3 + Vite

### 主选理由
- 开发效率高，适合快速搭建控制台和状态面板。
- 生态成熟，组件库选择丰富。
- Vite 冷启动与热更新体验好。

### 备选与放弃理由
- **React：** 同样可行，但若团队当前更偏 Vue，切换无明显收益。
- **Svelte：** 轻量，但团队熟悉度和生态覆盖可能不足。

### 结论
- 前端统一 Vue 3，减少跨项目切换成本。

## 4.4 数据库：PostgreSQL

### 主选理由
- 事务能力强，适合任务状态机与审计场景。
- JSONB 支持好，适合存储半结构化任务上下文。
- 生态成熟，迁移与运维经验广泛。

### 备选与放弃理由
- **MySQL：** 可用，但在复杂查询与 JSON 能力上略逊。
- **MongoDB：** 文档模型灵活，但事务与关系查询成本更高。

### 结论
- 核心元数据统一 PostgreSQL。

## 4.5 缓存与消息：Redis

### 主选理由
- 同时覆盖缓存与轻量消息流需求。
- Redis Stream 可满足 MVP 任务队列场景。
- 运维成本低、启动快、社区资料丰富。

### 备选与放弃理由
- **RabbitMQ：** 功能更完整，但引入与维护复杂度更高。
- **Kafka：** 适合大规模事件流，MVP 阶段过重。
- **NATS：** 很优秀，但团队若经验不足可能增加学习成本。

### 结论
- MVP 先用 Redis；后续若吞吐和可靠性需求上升再升级消息系统。

## 4.6 对象存储：MinIO / S3

### 主选理由
- MinIO 本地可快速搭建，兼容 S3 API。
- 便于后续迁移到云厂商对象存储。

### 备选与放弃理由
- **本地磁盘直存：** 简单但不利于扩展和多实例共享。

### 结论
- 开发测试用 MinIO，线上切 S3 兼容服务。

## 4.7 沙盒隔离：Docker

### 主选理由
- 容器隔离能力满足 MVP 安全基线。
- 可快速构建私有沙盒和共享集成环境。
- 与 CI/CD、镜像分发流程天然兼容。

### 备选与放弃理由
- **VM（KVM/虚机）：** 隔离更强但资源更重、启动更慢。
- **gVisor/Firecracker：** 安全性更高，但接入复杂度更高，适合后续阶段。

### 结论
- MVP 使用 Docker；生产加强阶段再评估更强隔离方案。

## 4.8 部署：docker-compose（MVP）

### 主选理由
- 一键拉起全套依赖，开发环境一致性高。
- 学习门槛低，适合快速验证与演示。

### 备选与放弃理由
- **Kubernetes：** 强大但 MVP 运维负担偏高。

### 结论
- MVP 统一 docker-compose；规模上来后迁移 K8s。

## 5. 关键横切能力选型

## 5.1 日志
- 格式：JSON 结构化日志。
- 字段基线：`timestamp`、`level`、`service`、`requestId`、`taskId`、`agentId`、`message`。
- 目标：支持按任务/Agent 追踪故障链路。

## 5.2 指标
- 基线指标：任务成功率、失败率、重试次数、平均执行时长、回滚次数、Token 消耗。
- MVP 可先输出到本地/数据库，后续接入 Prometheus + Grafana。

## 5.3 鉴权与安全
- API 使用 Token 鉴权（MVP 可先单租户 Token）。
- 密钥仅使用环境变量注入。
- 沙盒网络默认最小权限，按需放开出口。
- MVP 阶段告警通知可先采用 webhook 推送，避免过早引入独立消息告警平台。

## 6. 不做清单（MVP 阶段）

- 不引入分布式事务框架。
- 不引入多消息中间件并存。
- 不引入多云部署与复杂服务网格。
- 不引入企业级权限系统（RBAC/ABAC 全量版）。

## 7. 技术债与升级触发条件

## 7.1 Redis Stream -> 专业消息系统
- **触发条件：**
  - 消息堆积严重，消费延迟持续超阈值。
  - 需要更复杂的重放、分区、跨地域容灾。
- **升级候选：** NATS JetStream / Kafka / RabbitMQ（按场景决策）。

## 7.2 docker-compose -> Kubernetes
- **触发条件：**
  - 服务实例扩展超过单机能力。
  - 需要自动扩缩容、滚动发布、灰度策略。

## 7.3 Docker 沙盒 -> 强隔离沙盒
- **触发条件：**
  - 安全审计要求提升。
  - 多租户隔离要求提升。
- **升级候选：** gVisor / Firecracker。

## 8. 版本兼容与约束建议

- Go：建议 `1.23+`
- Node.js：建议 `20+`
- PostgreSQL：建议 `15+`
- Redis：建议 `7+`
- Docker：建议 `24+`

> 说明：具体版本可在实际搭建时按团队环境统一冻结到 `docs/Env-Baseline.md`。

## 9. 开发规范建议（与选型配套）

- 后端按领域模块化：`orchestrator`、`agent`、`contract`、`sandbox`、`timeline`、`delivery`。
- API 采用统一错误码与响应结构。
- 所有外部调用封装适配层，禁止在业务层直接耦合第三方 SDK。
- 所有关键状态流转必须写审计日志。

## 10. 结论

- 当前技术栈在 MVP 目标下是“成本最低、风险可控、扩展路径清晰”的方案。
- 核心思路是：**先跑通闭环，再强化可靠性与规模能力**。
- 该决策可支撑你在 8 周内交付可演示版本，并为后续生产化升级留足空间。
